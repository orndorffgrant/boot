# AGPLv3 Licensing and Source Offer — Design

Status: Implemented  
Date: 2026-11-14  
Decisions resolved: 2026-11-14  
Implemented: 2026-11-15  
Scope: repository licensing, build pipeline, `boot-api`, release assets, documentation  
Related: [release-and-update-design.md](release-and-update-design.md),
[releases.md](releases.md), [api-architecture-design.md](api-architecture-design.md)

## 1. Summary

Adopt the GNU Affero General Public License, version 3 (AGPLv3), for the
project and make the network source offer part of the build itself.

The design has five parts:

1. Add the canonical AGPLv3 license text and copyright notice, declare the
   license in Cargo metadata, and audit dependency licenses for compatibility.
2. Build a deterministic tar archive of the exact first-party source tree used
   to produce the binary and embed that archive with `include_bytes!`.
3. Serve the embedded archive from a public, unauthenticated
   `GET /v1/source` endpoint.
4. Build a full Linux dependency source bundle, compress it with xz, publish it
   as a release asset, and offer it at `GET /v1/source/dependencies` with
   metadata at `GET /v1/source/manifest`.
5. Verify in CI that both source levels are complete and match the bytes
   embedded or published by the build.

The first-party source archive is generated at build time. It is not read from
disk at runtime, so a deployed binary always carries the source for its own
build even if the deployment host has no source checkout. The dependency source
bundle is a release asset and is not embedded in the binary.

The design is implemented. The first-party archive is generated by
`boot-api/build.rs`, embedded in both release binaries, and published alongside
the release binaries. `tools/dependency-source.sh` generates the dependency
bundle from the full Linux normal-and-build graph for both release targets.

## 2. Current state

| Area | Current state |
| --- | --- |
| License file | No `LICENSE`, `COPYING`, or `NOTICE` file exists. |
| Cargo metadata | No `license` or `license-file` field in `[workspace.package]` or any crate. |
| Source offer | No API endpoint or other network offer. |
| Release assets | Raw `boot` binaries and SHA-256 checksums only. |
| Build artifacts | The release workflow builds `boot-cli` only; `boot-api` is a library inside that binary. |
| Source generation | No build script for `boot-api`; the only build script is `boot-api-client/build.rs`, which generates the typed HTTP client. |
| GitHub source archives | GitHub generates `Source code (zip)` and `Source code (tar.gz)` for each tag, but they are not tied to the built binary and do not satisfy the running-server offer by themselves. |

The API server currently binds to loopback by default and can be exposed on a
network with TLS. That means the running server can be used over a network, so
the project should treat the AGPL network-interaction obligation as applicable
even when the current deployment is local.

## 3. Licensing model

### 3.1 License choice

Use `AGPL-3.0-or-later` as the Cargo SPDX identifier.

The phrase "AGPL3" is ambiguous between "only version 3" and "version 3 or
later". This design recommends `AGPL-3.0-or-later` because:

- it matches the usual GNU recommendation for new projects;
- it avoids a future relicensing exercise if a later AGPL version is needed;
- the copyright holder can still distribute specific releases under the
  version 3 text.

This decision is resolved: use `AGPL-3.0-or-later`. If the project later needs
to prohibit later versions, the only changes are the Cargo identifier
(`AGPL-3.0-only`) and the notice wording. The rest of this design is unchanged.

### 3.2 Required license artifacts

| Artifact | Purpose |
| --- | --- |
| `LICENSE` | Canonical, verbatim AGPLv3 text from `https://www.gnu.org/licenses/agpl-3.0.txt`. |
| `NOTICE` | Copyright holder, AGPL notice, warranty disclaimer, and a pointer to the source offer. |
| `README.md` license section | Human-readable project license and source-download instructions. |
| `Cargo.toml` workspace metadata | `license = "AGPL-3.0-or-later"` in `[workspace.package]`. |
| Per-crate metadata | `license.workspace = true` in every workspace crate. |
| SPDX headers | Recommended on all first-party source files, including SQL migrations. |

The `NOTICE` should contain the standard "This program is free software..."
notice and end with:

```text
The running server offers the corresponding source for this exact build at
GET /v1/source. Release source archives are attached to each GitHub Release.
```

### 3.3 SPDX headers

Add `SPDX-License-Identifier: AGPL-3.0-or-later` headers to first-party Rust,
shell, configuration, and SQL files where the comment syntax is safe.

SQL migration files are included. No migration has run in any deployment yet,
so there is no applied-migration checksum to preserve. Add the header to the
existing migrations now, and require the same header on every new migration
from the start. SQL uses a `--` comment, for example:

```sql
-- SPDX-License-Identifier: AGPL-3.0-or-later
```

This keeps the repository consistent and avoids carving out an exception that
future migrations would have to remember.

If per-file headers are considered too noisy, the minimum acceptable set is
`LICENSE`, `NOTICE`, Cargo metadata, and the README. This design recommends
headers because they are more robust when a file is copied out of the
repository.

### 3.4 Third-party dependencies

This design covers the project's own source. It does not vendor every Cargo
dependency into the archive.

`Cargo.lock` is included, so the exact dependency versions are reproducible.
Most dependencies are permissively licensed and do not require their own source
offer, but the project still needs a positive check that none has terms
incompatible with AGPLv3.

Run that audit as part of this change:

- add a `deny.toml` allowlist for AGPL-compatible licenses (for example
  Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, MIT, Unicode-3.0, and Zlib);
- broaden the allowlist to `GPL-3.0-only`, `GPL-3.0-or-later`,
  `GPL-2.0-or-later`, `AGPL-3.0-only`, and `AGPL-3.0-or-later`;
- keep `GPL-2.0-only` denied because it is incompatible with AGPLv3;
- add LGPL and other weak-copyleft licenses as per-crate exceptions only after
  a relinking/source review;
- run `cargo deny check licenses` in CI;
- resolve an incompatible or unclear dependency before release, rather than
  shipping with a warning;
- generate `THIRD_PARTY_NOTICES.md` and include it in the dependency source
  bundle if a dependency's license requires notices.

Vendoring all dependency sources remains a non-goal. If one dependency's
license requires source distribution, vendor that dependency specifically and
document why.

## 4. Goals and non-goals

### 4.1 Goals

- The repository is unambiguously licensed as AGPLv3.
- Every binary built by the project carries the corresponding source for that
  exact build.
- The running server offers that source to every network user, without a
  token, payment, registration, or privileged scope.
- The offer is discoverable from ordinary API use, not only from a README.
- The published source archive is the same bytes that the binary embeds.
- The build fails rather than producing a binary with a missing or malformed
  source archive.
- Release builds are reproducible enough to audit: version, commit, archive
  hash, and build inputs are recorded.
- Local development remains practical and does not require a clean working
  tree.

### 4.2 Non-goals

- Providing legal advice or certifying compliance for third-party forks.
- Automatically covering an operator who patches a deployed binary without
  rebuilding it.
- Vendoring all Cargo dependencies into the archive.
- Adding a browser UI or a license-acceptance flow.
- Changing the authentication model for hardware endpoints.
- Changing `boot update` to download source. The updater continues to install
  binaries only.
- Adding compatibility shims or a second API version.

## 5. What the licence requires

This is a engineering summary, not legal advice.

- **AGPLv3 section 6 (conveying object code).** When a binary is conveyed, the
  recipient must be able to obtain the Corresponding Source. Attaching the
  source archive to the release and embedding it in the binary both help.
- **AGPLv3 section 13 (remote network interaction).** If a modified version is
  used to interact with users over a network, those users must be offered the
  Corresponding Source of that version from a network server at no charge.
- **AGPLv3 section 1 (Corresponding Source).** The source must be the preferred
  form for modification and must include the scripts and build inputs needed to
  generate, install, and run the object code.

The design therefore aims for an offer that is:

| Requirement | How this design satisfies it |
| --- | --- |
| Offered to all remote users | Public endpoint with no auth extractor and no token requirement. |
| At no charge | No payment, account, or license key. |
| Standard means of copying | Plain HTTP(S) download of an uncompressed tar archive with `Content-Disposition`. |
| Source of the running version | Archive is embedded at compile time from the same build inputs as the binary. |
| Preferred form for modification | Full workspace source, Cargo manifests, lockfile, build scripts, migrations, query cache, and docs. |
| Discoverable | `/v1/health` and `/v1/server` report the license and source URL; OpenAPI documents the endpoint. |

Two limits must be documented for operators:

1. If someone edits the source and rebuilds, the build-time archive should
   capture that edited tree. The release workflow uses a clean tagged tree;
   local builds use a working-tree fallback.
2. If someone patches a binary after it is built, or puts `/v1/source` behind
   an auth proxy, the automatic offer no longer describes or reaches the
   running version. No build mechanism can prevent that.

## 6. Source archive

### 6.1 Definition

The source archive is a single uncompressed tar file named:

```text
boot-<version>-source.tar
```

Inside the archive, every path is under one top-level directory:

```text
boot-<version>/
```

The archive is the project's Corresponding Source snapshot for that build. It
is target-independent: the x86_64 and aarch64 builds use the same source
archive bytes.

### 6.2 Contents

Include all first-party files needed to understand, modify, build, test, and
install the project. The simplest safe policy is to include every tracked file,
plus any uncommitted working-tree source in local builds.

| Path group | Included | Why |
| --- | --- | --- |
| `LICENSE`, `NOTICE`, `README.md` | Yes | License and offer. |
| `Cargo.toml`, `Cargo.lock` | Yes | Workspace and dependency resolution. |
| `.cargo/config.toml` | Yes | Offline SQLx query cache configuration. |
| `Cross.toml` | Yes | Release cross-build configuration. |
| `boot-protocol/` | Yes | Wire types. |
| `boot-api/` | Yes | Server, runtime, migrations, tests, udev data. |
| `boot-api-client/` | Yes | Generated-client build script and client wrapper. |
| `boot-cli/` | Yes | CLI source and migrations. |
| `.sqlx/` | Yes | Committed SQLx query cache used by offline builds. |
| `docs/` | Yes | Design and operational documentation. |
| `tools/` | Yes | Release and development scripts. |
| `.github/workflows/` | Yes | Reproducible release and test process. |
| `.gitignore`, `AGENTS.md` | Yes | Repository build/development context. |
| Test fixtures such as `boot-api/tests/fixtures/rtt.elf` | Yes | Included with the tests. |

Exclude these paths:

| Excluded path | Reason |
| --- | --- |
| `target/` | Build output; enormous and not source. |
| `.git/` | Not required for modification, can be large, and may contain historical secrets. |
| `dist/` | Generated release output. |
| `ext/` | Local external checkout, ignored by Git. |
| Local SQLite files (`*.sqlite3`, `*.sqlite`, `*.db`, `-wal`, `-shm`) | May contain tokens, sessions, or local state. |
| `*.env`, `.env.*` | Potential credentials. |
| TLS private keys and certificates (`*.key`, `*.pem`, `*.crt`) in local builds | Potential secrets; source does not need them. |
| Session logs, firmware artifacts, and local caches | Not source and potentially sensitive. |
| Editor/OS junk (`.DS_Store`, `*.swp`, etc.) | Noise. |

A generated archive must never include the archive itself. The archive is
written under `target/`, which is excluded.

The build should fail if `LICENSE` or `NOTICE` is missing from the archive.
This is the "automatically compliant" guard: a release cannot silently lose its
license or source offer.

### 6.3 Release mode

Release builds use a pre-generated archive from the tagged commit:

```text
tools/source-archive.sh --release --output target/source/boot-source.tar
```

The script:

1. Verifies the workspace version in `Cargo.toml`.
2. Refuses a dirty working tree (`git status --porcelain` must be empty).
3. Uses `git archive --format=tar --prefix=boot-<version>/ HEAD` so the
   archive is exactly the tagged tree.
4. Verifies that `LICENSE`, `NOTICE`, `Cargo.toml`, and `Cargo.lock` are
   present in the tar.
5. Writes `boot-source.tar` plus a small metadata sidecar with the version,
   commit, dirty flag, and SHA-256.

Using `git archive` for releases is deliberate:

- it cannot accidentally include `target/` or local databases;
- it records exactly the files in the tagged commit;
- it is deterministic for a given commit;
- it does not need a runtime source checkout.

The release workflow generates this archive once and passes the same file to
both target builds. The archive is not generated independently inside each
cross container.

### 6.4 Local development mode

A plain `cargo build` or `cargo test` should not require a clean tree or a
manually generated archive.

When no pre-generated archive is supplied, `boot-api/build.rs` creates one from
the working tree. The fallback:

- walks the workspace from the repository root;
- when `git` is available, uses `git ls-files --cached --others
  --exclude-standard` so tracked source and uncommitted, non-ignored source are
  included;
- when `git` is unavailable, walks regular files and applies the exclusion
  list above;
- records `dirty = true` if `git status --porcelain` is non-empty or the
  revision is unknown;
- still fails if `LICENSE` or `NOTICE` is absent.

The fallback exists for developer convenience. It is not the release path. It
may include extra untracked source, which is the correct behavior for a
modified local build: the running binary should offer the source that was
actually used.

Release CI always supplies the archive. A developer cross-build without it can
still use the filesystem-walk fallback; if the fallback cannot produce a
complete archive, it fails rather than embedding a partial one.

### 6.5 Determinism

The tar header must not depend on the machine, checkout time, or user:

| Header field | Value |
| --- | --- |
| Path order | Sorted by path bytes. |
| Entry mtime | `SOURCE_DATE_EPOCH` when set, otherwise `0`. |
| UID/GID | `0/0`. |
| User/group names | Empty. |
| Mode | Preserve executable bit; normalize files to `0644` and executables to `0755`. |
| Format | POSIX ustar or GNU tar; no PAX timestamps with the current time. |
| Compression | None. The asset is a plain `.tar`. |

For release mode, `git archive` is already deterministic for a commit. The
script should still verify the resulting SHA-256 and record it.

### 6.6 Archive metadata

The final archive itself contains only source; it does not contain a generated
metadata file that could differ between local and release builds. Build
metadata lives in a sidecar and in the binary:

```text
boot-source.meta
  version=<workspace version>
  commit=<git commit or "unknown">
  dirty=<true|false>
  sha256=<archive sha256>
```

The endpoint exposes the same fields in headers and server status. This keeps
the tar itself a clean snapshot and lets the release asset and embedded bytes
be compared directly.

## 7. Build-time embedding

### 7.1 Build flow

```text
release CI                         local cargo build
     │                                    │
     ├─ tools/source-archive.sh           ├─ no pre-generated tar
     │  (git archive HEAD)                │
     ▼                                    ▼
target/source/boot-source.tar     boot-api/build.rs working-tree fallback
     │                                    │
     └──────────────┬─────────────────────┘
                    ▼
          boot-api/build.rs
          - validate LICENSE/NOTICE
          - compute SHA-256
          - copy archive to OUT_DIR/source.tar
          - emit cargo:rustc-env metadata
                    │
                    ▼
          include_bytes!(OUT_DIR/source.tar)
                    │
                    ▼
          boot-api/src/source.rs
                    │
                    ▼
          boot-cli binary (both target triples)
                    │
                    ▼
          GET /v1/source
```

`boot-cli` depends on `boot-api`, so the archive is linked into the shipped
`boot` binary. No separate data file is installed next to the binary.

### 7.2 New build script

Add `boot-api/build.rs`.

Resolution order for the archive:

1. `BOOT_SOURCE_TARBALL`, absolute or relative to the workspace root.
2. `$CARGO_TARGET_DIR/source/boot-source.tar`, when `BOOT_SOURCE_REQUIRED=1`.
3. `<workspace>/target/source/boot-source.tar`, when
   `BOOT_SOURCE_REQUIRED=1`.
4. Working-tree fallback otherwise.

The target-directory candidates are gated on `BOOT_SOURCE_REQUIRED` so a local
build cannot silently embed a stale release archive left under `target/`.
Release builds fail if no archive is found.

The build script must print `cargo:rerun-if-changed` and
`cargo:rerun-if-env-changed` directives for the archive, the metadata sidecar,
and the workspace source directories, so editing another crate updates the
embedded source.

The script writes `OUT_DIR/source.tar` and emits:

```text
BOOT_SOURCE_SHA256=<hex>
BOOT_SOURCE_FILENAME=boot-<version>-source.tar
BOOT_SOURCE_REVISION=<commit or unknown>
BOOT_SOURCE_DIRTY=<true|false>
```

Release builds set `BOOT_SOURCE_REQUIRED=1`. If the pre-generated archive is
missing, the build fails. A release binary must never fall back silently.

### 7.3 Embedded module

Add `boot-api/src/source.rs`:

```rust
pub const ARCHIVE: &[u8] = include_bytes!(concat!(env!("OUT_DIR"), "/source.tar"));
pub const SHA256: &str = env!("BOOT_SOURCE_SHA256");
pub const FILENAME: &str = env!("BOOT_SOURCE_FILENAME");
pub const REVISION: &str = env!("BOOT_SOURCE_REVISION");
pub const DIRTY: bool = matches!(env!("BOOT_SOURCE_DIRTY"), "true");
```

The module should be compiled with the `run` feature, since only the server
needs it. The build script still runs for other `boot-api` consumers; it can
skip archive generation when the `run` feature is not enabled.

The archive is linked into `.rodata` and served by reference. It is not copied
on every request.

### 7.4 Binary size

At the time of this design, a source archive of the workspace is about 1 MiB
uncompressed. The binary grows by roughly that amount per target. That is an
acceptable cost for a self-contained source offer. Compression is not used
because the requirement is a tar and the artifact is small enough to serve
directly.

If size becomes a problem, a future design can serve a gzip-compressed tar with
`Content-Encoding: gzip` while keeping the same endpoint and tar contents.

## 8. API endpoint

### 8.1 Endpoint definition

Add one endpoint to the `BootApi` trait:

```text
GET /v1/source
```

It has no `Auth<_>` extractor. It is intentionally public.

The handler returns `FreeformBody` with the embedded bytes and sets the
response headers explicitly.

### 8.2 Response contract

```http
HTTP/1.1 200 OK
Content-Type: application/x-tar
Content-Length: <exact archive length>
Content-Disposition: attachment; filename="boot-<version>-source.tar"
ETag: "<sha256>"
Cache-Control: public, no-cache
X-Content-Type-Options: nosniff
X-Boot-Source-Sha256: <sha256>
X-Boot-Source-Revision: <commit or unknown>
```

The body is the exact archive bytes that were embedded at build time.

No `404` is expected in a correctly built binary; a missing archive is a build
failure, not a runtime condition.

### 8.3 Public OpenAPI metadata

`apply_security()` in `boot-api/src/lib.rs` currently special-cases
`/v1/health` as public. Add `/v1/source` to the public set so the generated
OpenAPI document does not claim that a bearer token is required.

Add tests that assert:

- `/v1/source` has an empty `security` array;
- the endpoint appears exactly once in the OpenAPI paths;
- the generated client still compiles.

### 8.4 Discoverability

To make the offer visible during ordinary API use, extend `ServerStatus` with:

```text
license: "AGPL-3.0-or-later"
source_url: "/v1/source"
source_sha256: "<archive sha256>"
source_revision: "<commit or unknown>"
source_dirty: <bool>
```

Both `GET /v1/health` (public) and `GET /v1/server` (read scope) return these
fields. A remote user can discover the offer without knowing the URL in
advance.

This changes the `boot-protocol` DTO and the generated client. There are no
existing deployments, so the fields can be required rather than optional.

Optionally, `boot show-server` can print the license and source URL. That is a
small UI improvement, not required for compliance.

### 8.5 Caching and special methods

- Do not require authentication, range requests, or a special `Accept` header.
- `If-None-Match` support is optional. `ETag` is provided so proxies and
  clients can validate a cached copy. Dropshot does not expose a ready-made
  304 response type in this version, so a v1 conditional-GET implementation
  would need custom response handling. Do not block the design on it.
- No server-wide middleware or event bus is added.

### 8.6 Example

```bash
curl -fSsOJ http://127.0.0.1:46673/v1/source
sha256sum boot-2026.1111.0-source.tar

tar -tf boot-2026.1111.0-source.tar | head
tar -xf boot-2026.1111.0-source.tar
cd boot-2026.1111.0
cargo build --release --locked
```

### 8.7 Dependency source offer

The second source level covers third-party dependencies:

| Endpoint | Behavior |
| --- | --- |
| `GET /v1/source/dependencies` | `302` redirect to the immutable dependency bundle asset; `503` if the build has no bundle. |
| `GET /v1/source/manifest` | `200` JSON with license, availability, URL, SHA-256, filename, targets, and package count. |

Both endpoints are public and must not be behind an auth proxy.

The dependency bundle is generated by `tools/dependency-source.sh`:

- `cargo vendor --locked` provides the complete crate source;
- the normal and build graph for `x86_64-unknown-linux-gnu` and
  `aarch64-unknown-linux-gnu` determines which crates are included;
- `DEPENDENCY-SOURCES.json` records versions, license expressions, checksums,
  upstream URLs, vendor paths, and license files;
- `THIRD_PARTY_NOTICES.md` provides package-level notices;
- the archive is compressed with `xz -6`;
- the bundle and checksum are attached to the release.

The server embeds only the bundle URL and SHA-256, not the bundle itself. This
keeps the binary near 1 MiB larger than the base binary instead of adding
hundreds of megabytes.

The release build sets `BOOT_DEPENDENCY_SOURCE_REQUIRED=1`. The build script
reads `target/source/boot-dependencies.meta` and fails if the dependency bundle
metadata is missing. Local builds may omit the bundle; the manifest then
reports `available: false` and the redirect returns `503`.

## 9. Release assets

Extend the GitHub Release with:

| Asset | Content |
| --- | --- |
| `boot-<version>-source.tar` | The exact first-party archive embedded in both binaries. |
| `boot-<version>-source.tar.sha256` | SHA-256 checksum. |
| `boot-<version>-dependencies.tar.xz` | Full Linux dependency source bundle. |
| `boot-<version>-dependencies.tar.xz.sha256` | SHA-256 checksum. |

The first-party source archive is target-independent. The dependency bundle
covers the normal and build graph for both Linux release targets.

The release notes should include a short "License and source" section pointing
at both attached archives and the `GET /v1/source` endpoints.

`boot update` continues to use the binary and checksum assets only. After a
successful update and restart, the running server serves the new binary's
embedded source. With `--no-restart`, the old process continues serving the old
source, which still matches the running binary.

## 10. CI verification

### 10.1 Source job

Add a `source` job to the release workflow:

1. Check out the tagged commit.
2. Run `tools/source-archive.sh --release --output target/source/boot-source.tar`.
3. Verify the archive listing contains `LICENSE`, `NOTICE`, `Cargo.toml`,
   `Cargo.lock`, all four crates, and `boot-api/build.rs`.
4. Verify the archive listing contains no `target/`, `.git/`, database files,
   or private-key files.
5. Upload the tar and its checksum as workflow artifacts.

Add a `dependencies` job that:

1. Checks out the tagged commit and installs Rust.
2. Runs `tools/dependency-source.sh --output target/source/boot-<version>-dependencies.tar.xz --url <release-url>`.
3. Uploads the xz bundle, its checksum, and `boot-dependencies.meta`.

### 10.2 Build jobs

The build jobs download both source artifacts into `target/source` before
running `cross build`. They set `BOOT_SOURCE_REQUIRED=1` and
`BOOT_DEPENDENCY_SOURCE_REQUIRED=1`, so missing or malformed source metadata
fails the build. Both target builds embed the same first-party source bytes and
the same dependency URL/SHA-256 metadata.

If a cross container does not expose the host target directory at the path the
build script expects, add a global `[build.env]` passthrough entry in
`Cross.toml` for `BOOT_SOURCE_TARBALL` and pass a workspace-relative path.
This should be verified with a dry run before the first release that uses the
mechanism.

Both target builds check that the expected archive SHA-256 string is present
in the binary. The x86_64 build also starts the freshly built binary on a
loopback port, downloads `/v1/source`, and compares it byte-for-byte with the
source artifact that was passed into the build. This catches a cross-container
path or environment mistake before release.

### 10.3 Test job

Add tests that do not require hardware:

- The archive has a single top-level `boot-<version>/` directory.
- `LICENSE` and `NOTICE` are present.
- Every `git ls-files` path exists in the archive.
- Forbidden paths are absent.
- The archive's SHA-256 matches the embedded `source::SHA256`.
- `/v1/source` returns `200` without an `Authorization` header.
- The response bytes equal `source::ARCHIVE`.
- The response `Content-Type`, `Content-Disposition`, `ETag`, and
  `Content-Length` are correct.
- `/v1/source/manifest` returns `200` without an `Authorization` header.
- `/v1/source/dependencies` returns `302` when configured and `503` when not.
- `/v1/health` and `/v1/server` report both source levels.
- OpenAPI marks all three source endpoints as public.

### 10.4 Dependency license audit

Run `cargo deny check licenses` in CI using the committed `deny.toml`
allowlist. A license that is missing, unknown, or outside the AGPL-compatible
allowlist fails the check and blocks the release.

The audit does not vendor dependencies. If a dependency requires notice text,
generate `THIRD_PARTY_NOTICES` and include it in the source archive.

### 10.5 Optional rebuild check

A release-only CI job can extract the source archive, run
`cargo build --release --locked`, and confirm that the extracted source builds.
This is the strongest practical check that the archive is complete. It adds a
full build to CI, so it can be a manual release step if time is constrained.

The operator documentation must state explicitly:

- `/v1/source` must not be placed behind an auth proxy.
- The endpoint describes the binary that is currently running.
- A source checkout is not required on the deployment host.
- A locally modified build should be rebuilt with the source-archive fallback so
  the served source includes the modification.

## 12. Security and operational considerations

### 12.1 The archive is public

The endpoint is unauthenticated by design. The archive must contain no secrets.
The exclusion list and the CI listing check are security controls, not just
hygiene. In particular, never include:

- `.git/`;
- `target/`;
- `boot.sqlite3`, `boot-cli.sqlite3`, or their `-wal`/`-shm` files;
- `.env` files;
- TLS private keys;
- uploaded firmware or session data.

### 12.2 Denial of service

The response is a static in-memory body of roughly 1 MiB. It performs no
database, hardware, or filesystem work per request. Normal HTTP connection
limits, reverse-proxy limits, and cache headers are the intended mitigations.
Do not require a token to reduce load; that would undermine the offer.

### 12.3 Source leaks

If a local developer builds from a tree containing untracked files, the
fallback archive may include them. That is intentional for matching a modified
build, but developers should know that a locally run server publishes the
workspace source to network users. The exclusion list keeps the common local
state out of the archive. Release builds use `git archive` and cannot include
untracked files.

### 12.4 Proxy and deployment configuration

Deployers who put the API behind a reverse proxy must allow
`GET /v1/source` without authentication. This should be in the deployment
documentation and in the release notes, because it is the one endpoint whose
compliance depends on deployment behavior.

### 12.5 Update interactions

- `boot update` replaces the binary; the source follows automatically.
- A failed update leaves the old binary and therefore the old source.
- `--no-restart` leaves the old process and old source running.
- A rollback restores the old binary and the old source.
- The endpoint never reads from the installation directory, so replacing the
  binary does not create a window where the source and binary disagree.

## 13. Alternatives considered

| Alternative | Why not chosen |
| --- | --- |
| Link to GitHub source only | Does not cover private forks, deleted releases, offline deployments, or the exact running build. |
| Rely only on GitHub's auto-generated source archives | Not tied to the binary, not served by the running server, and not guaranteed to match local or modified builds. |
| Read source from disk at runtime | Requires a source checkout on every deployment host and can serve source that does not match the binary. |
| Serve a zip or tar.gz | The requirement is a tar; plain tar avoids compression dependencies and content-negotiation complexity. |
| Add auth to the source endpoint | Violates the "all users interacting remotely" intent and adds a compliance failure mode. |
| Embed all Cargo dependency sources | Large; dependency licenses are separate works. Revisit if the dependency audit requires it. |
| Generate the archive only in CI | A local or custom build would have no source offer. The build-time fallback keeps local builds useful. |
| Store the archive as a separate sidecar file next to the binary | Can be lost or mismatched; the server cannot reliably find it; the source offer would not be self-contained. |
| Build a custom zip/tar section appended to the executable | More format work and tooling; `include_bytes!` already gives a self-contained binary. |

## 17. Risks

| Risk | Mitigation |
| --- | --- |
| The archive accidentally includes a secret. | Exclusion list, CI listing check, and release-only `git archive`. |
| The archive misses a file needed to rebuild. | Compare against `git ls-files` and, optionally, rebuild from the archive in CI. |
| A cross container cannot see the pre-generated tar. | Put it under `target/source/`, resolve `CARGO_TARGET_DIR`, and set `BOOT_SOURCE_REQUIRED=1` only after the path is verified in CI. |
| Binary size grows. | About 1 MiB at current size; compress later if needed. |
| A proxy blocks or authenticates the source endpoint. | Document the requirement; include it in release/deployment checks. |
| A fork modifies the binary without rebuilding. | Document that the offer covers builds produced by this build process, not post-build patches. |
| AGPL compatibility of a dependency. | `cargo deny check licenses` in CI; incompatible dependencies block release. |
